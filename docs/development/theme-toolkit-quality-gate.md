# Theme toolkit quality gate

This is the maintained acceptance supplement to the original design in
`dist/THEME_DEVELOPMENT_TOOLKIT.md`. The `dist/` directory is ignored by Git;
this document keeps the reviewed requirements and verification procedure in
version control.

## Review findings and requirement changes

The original workspace tests passed before this review. Successful scaffolding,
rendering and reproducible packaging were covered, but that did not establish
safe behavior for failed operations or adversarial metadata. Running the first
13 new CLI regression tests against the original implementation reproduced seven
failures: argument prevalidation, scaffold symlink protection, ZIP cleanup, README
escaping, predictable temporary ZIP links, invalid artifact destinations and
unsafe file paths. The fixed implementation passes those cases.

| Finding | User impact | Required behavior |
|---|---|---|
| Invalid later CLI arguments were validated after earlier prompts | A script could wait for input instead of reporting its invalid author or URL | Validate every supplied argument before prompting; gather all answers before writes |
| Existence checks followed symlinks | A dangling scaffold target could create files outside the project | Reject existing targets including dangling links; reject symlinked scaffold parents |
| Filesystem paths were normalized before validation | A Unix backslash filename could alias a different download path | Validate original paths; normalize native separators only on Windows; reject empty segments, dot segments, absolute paths, backslashes, colons and control characters |
| Theme-directory symlinks were not checked by traversal | A project could test and modify a theme outside its directory | Reject links in `.cac`, `.cac/themes`, the selected theme directory and all entries before reading or rendering the theme |
| Markdown escaping left raw HTML and block syntax intact | A published README could contain injected HTML, headings or table rows | Render editable metadata as literal text; escape HTML, Markdown and URL contexts separately; flatten metadata line breaks in generated prose and table cells |
| Manifest validation accepted self hashes and noncanonical paths | An accepted package could be ambiguous or impossible to verify | Forbid `theme.json` in `files`; require unique canonical paths and 64 lowercase hexadecimal hash characters |
| Final verification checked only declared files | Undeclared content could silently disappear from the release | Compare the full regular-file inventory against the manifest, then verify all hashes; hash the actual bytes added to the ZIP again |
| Testing rewrote every source and wrote artifacts directly | Read-only source files could fail testing; a bad output destination could leave mixed artifacts | Do not rewrite source/assets/fonts; validate output destinations and stage all generated bytes before replacing successful files |
| Packaging used a predictable temporary path and leaked it after rename errors | An unrelated linked file could be overwritten, or partial ZIPs left behind | Use unique temporary files with automatic cleanup and replace the final ZIP only after finishing it |
| Schema documented but did not require the selected theme | Editors could accept incomplete theme-project settings | Schema requires `theme` when `themeProject` exists; runtime validates their equality |

## Acceptance matrix

All automated cases below run in the normal workspace test suite. CLI regression
cases are in `crates/cac/tests/theme_quality_gate.rs`; existing command tests
remain in `command_tests.rs`. Metadata and checksum boundary cases have unit
coverage beside their implementations. Renderer cases are in
`crates/cac-render/tests/render_tests.rs`.

| Gate | Required evidence |
|---|---|
| Initialization | Complete argument input; interactive retries and omitted URL; EOF at every prompt leaves an empty directory; all invalid/reserved names and invalid authors/URLs fail; existing targets retain their bytes; ordinary init omits `themeProject` |
| Project identity | Settings round-trip uses exact `themeProject`; schema requires `theme`; missing/mismatched/invalid markers fail test and pack; normal build and local discovery still work |
| Restrictions | Installation fails before registry access; selected development theme cannot be removed; unrelated local theme can be removed |
| Editable manifest | Missing description/license, invalid author/URL, mismatched name, unsupported API and missing entrypoint fail; invalid Typst preserves previous generated artifacts and ZIP |
| Paths | Unsafe original filenames, nested symlinks and a linked theme root fail before output changes; dangling init targets and linked scaffold parents do not write outside the project; unsupported socket entries fail; read-only theme source remains usable and unchanged (Unix tests) |
| README | Linked and unlinked authors, Unicode, pipes, brackets, raw HTML, injected headings and multiline license values remain text; link punctuation is encoded |
| Rendering | Decode JPEG bytes, check actual image dimensions for US Letter (612 × 792) and A4 (595 × 842), check white page corners and visible ink; check PDF signature; rendering resolves the project theme |
| Inventory | Nested Unicode assets and font-directory files are included; manifest self hashes, duplicate paths, missing required files and malformed hashes fail; modified, missing and undeclared files fail final verification |
| ZIP | Exact sorted entry list, top-level theme directory, manifest bytes, every archived checksum, fixed timestamps and file permissions; no validation PDF; repeated packaging has identical bytes |
| Failure preservation | Broken render leaves all successful artifacts unchanged; invalid PDF destination leaves other artifacts unchanged; failed ZIP replacement cleans temporary files; predictable temporary-name symlinks are never followed |
| Compatibility | Existing registry/install tests and help snapshots pass; Theme API constant agrees with embedded Typst API |

JPEG encoding uses quality 90 and one pixel per Typst point. Dimensions are those
of the actual rasterized first page; A4 rounding is determined by the renderer.
The PDF and preview are derived from one compiled document. Empty asset/font
directories do not need archive entries. Every regular theme file is downloadable,
so contributors must remove private notes and unused source assets before packing.
The initial MIT license is a valid default; authors must confirm or change it,
but the CLI cannot verify ownership or a human's license review. A nonempty
meaningful description is required; the software checks that it is nonempty.

## Release procedure

Run all four commands successfully on the final tree:

```console
cargo test --workspace --all-features --locked
cargo fmt --all --check
cargo clippy --workspace --all-features --all-targets --locked -- -D warnings
cargo build --release --locked --package cac
```

For a focused iteration:

```console
cargo test -p cac --locked --test theme_quality_gate
cargo test -p cac --locked --bin cac
cargo test -p cac-render --locked --test render_tests
```

No new help syntax is introduced by these fixes. Existing valid themes retain
their manifest format and archive layout. Previously accepted unsafe paths and
self-hashed manifests are now rejected; generated README escaping can change
README hashes and archive bytes on the first retest.

## Human checks and limits

Before publishing an individual theme, inspect its generated PDF and preview with
minimal, long, multipage and multilingual CVs. Confirm readable contrast, sensible
page breaks, no clipped content, correct glyphs and intended first-page composition.
Compilation and checksum success cannot establish visual quality. Also confirm
font/asset redistribution permission and the description's usefulness to users.

Run the suite on Linux and Windows as well as macOS before claiming platform-wide
acceptance. Symlink tests are Unix-only. EOF is automated; actual terminal Ctrl-C
should additionally be exercised during each prompt and leave no scaffold.
Disk-full and process termination during final artifact replacement are not
fault-injected by this gate. Each generated file is replaced atomically, but the
four generated files are not a filesystem-wide transaction. Concurrent editing
or two simultaneous theme test/pack operations on the same project are outside
this gate; keep the project stable while a command runs.
